# flying-orm V1.0.1 变更说明

V1.0.1 的重点不是扩展功能数量，而是让 V1.0.0 已有能力更容易接入、更容易维护，并让事务和日志在真实应用
框架中保持一致、可控、可观测。

## 主要变化

- 拆分动态表单渲染、R2DBC 执行、批量写入、条件编译、实体映射、Schema 和运行时装配中的大型职责。
- 新增框架无关的 `FlyingOrmConfiguration`、`FlyingOrmEnvironment` 和统一 `FlyingOrmClients` 启动入口。
- 显式方言优先；未配置时从 `ConnectionFactory` 自动识别；无法识别时启动失败。
- 建立统一外部事务参与契约。外部事务存在时，CRUD、原生 SQL、Repository、FormClient 和 ATOMIC 复用同一连接，
  flying-orm 不重复提交、回滚或关闭连接。
- 外部事务中的 ATOMIC 返回 `ENLISTED`，并在事务真正结束后报告最终状态；INDEPENDENT 在 SQL 前拒绝。
- 动态数据源在事务开始前路由，事务期间锁定物理数据库和主库读取。
- SQL 日志支持类型、状态、耗时、返回/影响行数、事务来源和批量摘要；SQL 与参数默认关闭，开启后统一脱敏和截断。
- 普通 observer 使用无事务解析快路径；只有明确需要事务来源的 observer 才读取事务上下文。
- V1.0.1 新增精确公开 API 快照，同时继续检查 V1.0.0 公开签名没有删除或改变。

## 兼容性

V1.0.0 已有公开签名继续保留。V1.0.1 的新配置、事务和日志能力采用增量入口，默认情况下不会开启完整 SQL、
参数日志或外部事务适配。

同步 API 仍是同一 R2DBC 内核的最外层阻塞桥，不是 JDBC 双内核。真正 JDBC 执行内核属于 2.0.0 规划。

主项目没有 Spring、starter 或日志框架依赖。Spring Boot 只是平级示例项目中的首个适配验证，其他 Java 容器可以
实现同一配置和事务参与契约。

## 性能与内存

- 完整 JMH 共 25 个场景。SQL 渲染和执行保护保持稳定，普通 observer 相对阶段基线下降 `2.25%`，在门禁内。
- 结构化日志开启路径为 `474.156 ns/op、2384 B/op`；默认关闭路径不创建该 observer。
- 动态行继续使用紧凑列布局，Map API 不要求每行创建完整 LinkedHashMap 桶结构。
- 批量输入保持流式有界消费，不收集整个 Publisher；元数据与计划缓存继续使用有容量和失效规则的 Caffeine。
- MySQL/PostgreSQL 真实库功能、事务、故障和并发场景实际执行 33 个，全部通过。
- 两库完成固定参数三轮性能认证；MySQL updateById 另做三轮单场景复核，与稳定参考持平。

完整证据见 [V1.0.1 真实数据库与性能认证](database-certification-2026-08-07-v1.0.1.md)。

## 质量门禁

- `mvn -Pquality clean verify`：全模块通过，覆盖率、SpotBugs、Checkstyle、API 基线和依赖收敛通过。
- `mvn -Prelease-artifacts verify`：主 JAR、源码包、Javadoc 包和直接依赖分析通过。
- `V1PublicApiBaselineTest`：V1.0.0 向后兼容与 V1.0.1 精确冻结快照均通过。
- 本次只完成本地制品验证，没有上传到 Maven 仓库。

## 已知环境边界

Windows Docker 严格同步写环境仍可能出现 MySQL 单次长尾抖动。当前证据没有发现连接泄漏、无限并发、业务错误
或 ORM updateById 路径退化；正式生产容量结论仍应在部署目标的 Linux、磁盘和数据库配置上复跑。
