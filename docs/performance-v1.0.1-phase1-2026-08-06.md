# V1.0.1 阶段 0/1 无数据库性能回归

本轮只验证 V1.0.1 首批职责拆分有没有拖慢动态表单 SQL 渲染和响应式执行包装，不连接真实数据库，
也不把这次短跑当成最终 RC 性能认证。

## 比较对象

- 基线：V1.0.0 最后收口提交 `f22c9f4ff635a0c78514837bd5eade94c2f2434a`。
- 当前：`1.0.1` 工作区完成 `FormDataSqlRenderer`、`R2dbcSqlExecutor` 和
  `ObservedReactiveSqlExecutor` 首批拆分后的代码。
- 环境：同一台机器、Oracle JDK 21.0.10、JMH 1.37、单线程、1 fork。
- 参数：3 次 1 秒预热，5 次 1 秒测量，启用 GC profiler。

原始证据：

- [V1.0.0 基线 JSON](performance-results/2026-08-06-v101-phase1-baseline.json)
- [V1.0.1 最终 JSON](performance-results/2026-08-06-v101-phase1-final.json)
- [自动比较报告](performance-results/2026-08-06-v101-phase1-comparison.md)

## 结果

| 场景 | 基线 | 当前 | 变化 | 分配变化 |
| --- | ---: | ---: | ---: | ---: |
| SQL 热计划命中 | 892.072 ops/ms | 970.442 ops/ms | +8.79% | 3808.015 -> 3832.018 B/op，+0.63% |
| SQL 关闭计划缓存 | 270.557 ops/ms | 292.187 ops/ms | +7.99% | 16200.026 -> 15280.024 B/op，-5.68% |
| 条件 where 渲染 | 674.225 ops/ms | 690.211 ops/ms | +2.37% | 7624.010 -> 7576.010 B/op，-0.63% |
| SQL 观测包装 | 244.034 ns/op | 238.705 ns/op | 耗时改善 2.18% | 744.002 -> 744.002 B/op，持平 |

首轮拆分后，热计划命中曾出现 264 B/op 的稳定分配增加。JFR 定位到 `fieldNames()` 的 Stream 临时对象在
跨类拆分后不再被 JIT 稳定消除，因此改为预分配列表和直接循环。修正后的独立复测为基线 948.140 ops/ms、
当前 946.356 ops/ms，吞吐差 -0.19%；分配差从 6.93% 降到 1.89%。最终整组复跑中分配差进一步收敛到
0.63%，没有有效场景越过 5% 退化线。

`directUpdate` 和 `protectedUpdate` 低于 1 ns/op，可能被 JIT 常量折叠，继续按既有规则排除，不用于任何性能结论。
吞吐模式 JSON 中的 percentiles 是每轮吞吐分布，也不是请求延迟 P95/P99。

## 结论

阶段 0 的当前基线和阶段 1 的首批重构回归已经闭环。现有证据表明公开行为保持不变，相关纯 Java 热路径没有
性能退化；冷计划和观测包装还有小幅改善。真实数据库吞吐、连接池、取消、批量事务及 P95/P99 继续放在最终认证阶段。
