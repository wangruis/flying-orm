# flying-orm v2.0.0 JDBC/R2DBC 双执行内核规划

> 本规划建立在全部 V1.x 能力之上。V2 不重做 ORM，也不复制条件、SQL、安全、事务或映射逻辑；它只把真正的
> JDBC 执行能力接入现有统一内核，并让 JDBC 与 R2DBC 使用同一套业务入口。

## 一、版本目标

flying-orm 仍然是一个独立、简单、易用、稳定、安全，并为动态表单而生的 ORM。先保证调用容易理解、默认行为安全、
事务结果可信和故障可排查，再追求高性能、低延迟、高并发与高吞吐。

V2.0.0 的核心目标：

1. 在现有 R2DBC 真响应式内核之外增加真正的 JDBC 执行内核。
2. JDBC 和 R2DBC 共享动态表单、实体 Repository、条件 AST、Scope、SQL 渲染、方言、codec、参数顺序、批量结果、
   执行保护、错误分类和观测模型。
3. 业务代码使用同一套 FormClient、Repository、DatabaseOperator、DDL、DML 和参数化原生 SQL；切换执行方式时不重写
   查询和写入逻辑。
4. 上层事务管理器是唯一事务控制者。flying-orm 自动加入上层事务，不要求业务代码传连接或手工提交、回滚、关闭。
5. 纯 Java 和各类 Java 容器使用同一套框架无关接入契约。Spring/Spring Boot 作为首个完整示例，但不能进入 core/rdb。
6. SQL 日志由上层日志系统和正常日志级别管理，不要求业务应用维护一组日常用不到的 ORM 日志开关。

## 二、不可突破的边界

- 响应式 API 只使用 R2DBC，必须端到端非阻塞。禁止把 JDBC 包进 Reactor，也禁止在事件循环中执行阻塞访问。
- 同步 API 只使用原生 JDBC，响应式 API 只使用原生 R2DBC。V2 删除既有 R2DBC 阻塞同步桥接，不保留兼容开关。
- “无缝切换”表示业务 DSL、实体、动态表单、Scope、安全规则和结果语义不变，不表示阻塞与响应式返回类型可以混用。
- core/rdb 不依赖 Spring、Spring Boot、starter 或任何应用容器；本仓库不增加 Spring 模块。
- JDBC 实现放在现有 `flying-orm-rdb`，不为每个执行方式复制 form、repository、schema 或 dialect 模块。
- V1 已有功能不能因为接入 JDBC 而缩水。两条执行链对相同请求必须生成等价 SQL，并保持相同参数顺序和错误语义。
- 不引入新的大型类。生产类型通常不超过 300 行和 20 个可调用方法，达到门限前按真实职责拆分。
- 默认安全不能靠文档提醒。参数绑定、Scope、写入条件保护、执行上限、资源关闭和日志脱敏必须由内核强制执行。

## 三、使用体验目标

### 3.1 普通业务调用

业务层继续使用统一入口，不感知 renderer、dialect 或底层 executor：

```java
repository.findById(id);

createQuery()
        .where("name", name)
        .fetch();

createUpdate()
        .set(user::getName)
        .where(user::getId)
        .execute();
```

动态表单、跨表 `DatabaseOperator`、DDL/DML 和安全原生 SQL 同样通过现有门面调用。执行方式由启动时提供的连接能力决定，
不能要求每个业务方法选择 JDBC 或 R2DBC。

### 3.2 最少接入信息

上层只需要提供以下能力：

- JDBC 应用提供 `DataSource`；响应式应用提供 `ConnectionFactory`。
- `flying-orm.dialect` 可以明确配置；未配置时从 JDBC URL/metadata 或 R2DBC metadata 自动识别。
- 动态数据源提供当前路由和全部物理库的方言校验信息。
- 使用上层事务时，适配层把“当前事务连接”交给统一事务参与契约。

业务代码不手动创建 `ReactiveFormClient`、`DatabaseOperator`、renderer、dialect 或 executor，也不手工传递事务连接。

### 3.3 实体注解与主键生成

V2 使用 flying-orm 自己的实体注解，不依赖、反射读取或要求用户引入 Jakarta Persistence。注解放在
`com.flying.orm.core.annotation`，名称和常用语义尽量贴近常见 Java ORM，降低学习成本，但底层实现、
元数据模型和执行逻辑全部由 flying-orm 独立完成：

- `@TableName(value, schema)`：表名和可选 schema；遵守命名约定时可以省略。
- `@TableId(value, type)`：主键列和生成策略。`IdType` 提供 `NONE`、`AUTO`、`INPUT`、`ASSIGN_ID`、
  `ASSIGN_UUID`；默认 `NONE` 跟随全局策略，全局未配置时按安全的 `INPUT` 处理。
- `AUTO` 明确表示数据库自增。insert 必须省略该列，读取数据库生成键并通过统一插入结果返回；可安全写入的 JavaBean
  同步回填，record 等不可变实体不做破坏性反射写入。
- `INPUT` 由调用方赋值，SQL 前发现主键为空就返回稳定错误；`ASSIGN_ID`、`ASSIGN_UUID` 在 SQL 前生成。
- `@KeySequence` 负责 Oracle、PostgreSQL 等数据库序列，复用同一生成键结果和回填规则。
- `@TableField(value, exist, select, fill, insertStrategy, updateStrategy)` 表达列映射、非表字段、默认查询排除、
  填充和写入空值策略；`FieldFill` 提供 `DEFAULT`、`INSERT`、`UPDATE`、`INSERT_UPDATE`，`FieldStrategy` 提供
  `DEFAULT`、`ALWAYS`、`NOT_NULL`、`NOT_EMPTY`、`NEVER`。
- `@Version`、`@TableLogic(value, delval)`、`@EnumValue` 分别表达乐观锁、逻辑删除和枚举数据库值。
- `@OrderBy(asc, sort)` 只允许标在实体字段上，作为没有显式排序时的安全默认值；显式 DSL 排序优先。
- 不提供接受原始 SQL 的注解属性。更新表达式、条件和排序继续通过参数化 DSL 或启动期注册 SQL 模板表达。

V2 已移除实体映射链中的 `JakartaAnnotationReader`。这是 V2 允许的破坏性升级：用户把 Jakarta 实体注解迁移为
flying-orm 注解，DDL、DML、Repository、FormClient 和 DatabaseOperator 的调用入口不变。

主键生成继续遵守以下安全边界：

- 雪花生成器必须配置稳定且不冲突的 worker/node id；缺失、重复风险或时钟回拨越过安全边界时拒绝生成，不能静默
  产生可能重复的主键。
- 使用少量框架无关 `IdGenerator` SPI 承接应用自定义生成器。生成器在 SQL 前执行，JDBC/R2DBC、单条/批量使用
  同一实现和错误语义。
- 自动填充值由框架无关 provider 提供，内建创建时间和更新时间；当前用户、租户等上下文值由上层适配器提供，
  core/rdb 不依赖 Spring Security 或其他容器。
- 默认查询排除字段不会进入普通 `SELECT *` 投影，前端结构化条件和投影不能重新放开；可信 Java 代码显式选择时仍要
  经过 FieldScope 检查。
- 枚举成员访问计划进入有界实体元数据缓存，并在启动/首次解析时拒绝 null、
  重复数据库值和不支持的成员类型。

### 3.4 启动期实体扫描与表结构同步

实体表结构同步是框架无关能力。Spring Boot 只负责把 `application.yml` 转为同一个配置对象；Micronaut、Quarkus、
Jakarta CDI、自研容器和纯 Java 通过代码配置使用同一实现。同步过程固定为：扫描实体、编译元数据、读取真实数据库
结构、生成差异计划、风险分级、按策略处理、精确失效相关缓存、返回结构化结果。

- `OFF`：默认值，不扫描和修改数据库结构。
- `VALIDATE`：只校验表、字段、主键和索引差异；发现不一致时启动失败，不执行 DDL。
- `SAFE_UPDATE`：允许新建表、增加兼容字段、增加索引和安全扩宽类型；删除、重命名、缩窄类型、改变主键等危险操作
  只生成计划并拒绝启动。
- `FULL_UPDATE`：允许按差异计划执行删除字段、删除索引、类型变化等破坏性 DDL，必须由使用方显式开启，并通过现有
  DDL 风险审核和批准指纹；不允许因为处于开发环境就自动绕过审核。
- 实体扫描结果必须去重并检查表名、列名、主键、索引和生成策略冲突；多个实体意外映射到同一表时启动失败。
- DDL 链式 API 和动态表单 `createOrAlter` 保持现有调用方式。自动同步只负责启动编排，底层继续复用同一
  `DynamicForm`、Schema diff、方言渲染、DDL 审核、执行结果和缓存失效能力。
- 动态数据源先完成路由和方言确认，再逐个目标库生成并执行计划；事务期间不做隐式结构同步。

Spring Boot 示例配置：

```yaml
flying-orm:
  schema:
    mode: safe-update
    scan-packages: com.example.domain
```

纯 Java 使用类型化配置表达相同策略，不要求日志、事务或容器专用注解参与。

## 四、统一执行架构

### 4.1 共享层

以下能力只能保留一份实现：

- 动态表单、实体元数据和 `DynamicRow`。
- Java DSL、前端结构化条件、可扩展 term 和条件 AST。
- TenantScope、DataScope、FieldScope、TimeScope、逻辑删除和乐观锁。
- SQL 请求模型、方言渲染、命名参数解析、参数顺序和 codec。
- 执行保护、批量请求与结果、异常分类、事务结果和 observer 事件。
- Schema diff、DDL 审核、迁移计划和元数据缓存失效。

### 4.2 执行层

- `R2dbcSqlExecutor` 继续负责真正非阻塞的 R2DBC 执行。
- V2 新增 JDBC executor，使用 `DataSource`、`Connection`、`PreparedStatement` 和 `ResultSet` 原生执行。
- 两个 executor 消费同一个已经完成安全校验和方言渲染的 SQL 请求，不得各自重新解释条件或拼接 SQL。
- JDBC executor 必须支持 query timeout、fetch size、max rows、取消和完整的 try-with-resources 等价资源关闭。
- JDBC 行读取直接进入共享 `DynamicRow` 或实体映射计划，避免先创建临时 Map 再转换。
- 同步 JDBC 热路径不创建 Reactor Publisher；响应式热路径不创建 JDBC 适配对象。

### 4.3 统一启动

- 沿用少量框架无关启动门面，一次装配 Executor、FormClient、Repository、DatabaseOperator、Schema、Metadata、
  方言、codec、缓存、执行保护和 observer。
- 只提供 `DataSource` 时只装配同步 JDBC 能力；只提供 `ConnectionFactory` 时只装配响应式 R2DBC 能力。
- 应用声明需要同步能力却没有 `DataSource`，或者声明需要响应式能力却没有 `ConnectionFactory` 时，启动阶段直接失败，
  不能在运行时偷偷桥接到另一条执行链。
- 同时提供两者时，同步入口走 JDBC，响应式入口走 R2DBC；启动阶段验证两者指向的数据库类型和方言一致。
- 显式方言优先。自动识别失败、识别冲突或动态物理库方言不一致时直接启动失败，不能猜一个默认方言继续运行。

## 五、统一事务策略

一次数据库调用只能有一个事务控制者：

1. 上层事务存在时，所有 CRUD、FormClient、Repository、DatabaseOperator、DDL/DML、参数化原生 SQL 和 `ATOMIC`
   批量都使用上层事务绑定的同一物理连接。
2. flying-orm 加入外部事务后不再 begin、commit、rollback 或关闭连接。最终提交、回滚或未知状态由外部事务完成信号
   和统一事务 observer 表达。
3. 外部事务中的 `ATOMIC` 只能先返回 `ENLISTED`，表示 SQL 已执行并加入事务，不能在外部提交前谎报 `COMMITTED`。
4. `INDEPENDENT` 会独立提交分片，与外部整批事务冲突；检测到外部事务时必须在执行任何 SQL 前拒绝。
5. 没有外部事务时，普通操作按连接默认提交语义执行；显式事务和 `ATOMIC` 批量由 flying-orm 自己控制并返回明确结果。
6. JDBC 与 R2DBC 使用相同的事务状态、错误和观测模型，但分别通过各自连接类型执行，不用通用接口掩盖阻塞差异。
7. 动态数据源必须在事务开始前完成路由。事务期间锁定物理数据库，事务内读取走主库，不承诺跨库本地事务原子性。
8. Spring 示例只使用标准 `@Transactional`；纯 Java 和其他容器通过同一事务参与 SPI 接入，不增加 Flying 专用事务注解。

## 六、SQL 日志与故障观测

日志由上层项目的日志系统管理。Spring Boot 示例的日常配置只需要：

```yaml
logging:
  level:
    com.flying.orm.sql: DEBUG
```

日志契约：

- DEBUG 开启时输出参数化 SQL、参数值、SQL 类型、JDBC/R2DBC 执行方式、事务来源、耗时、返回行数、影响行数和批量摘要。
- 参数按顺序输出，例如 `parameters=[1:"张三", 2:100]`，不能让排查人员自己猜占位符对应哪个值。
- 慢 SQL、超时、取消、连接异常和 `UNKNOWN` 至少以 WARN 记录；执行、提交、回滚或资源释放失败以 ERROR 记录。
- 慢 SQL 使用内建默认阈值 1 秒。DEBUG 已开启时，慢 SQL 记录完整安全信息并标记 `slow=true`；未开启 DEBUG 时，
  WARN 仍保留不含敏感参数的安全摘要。
- 不要求常规应用配置 `full-sql`、`parameters`、`max-value-length` 或 `max-message-length`。这些保护使用安全的内建默认值，
  真正有特殊需要时才允许通过程序化高级配置覆盖。
- 密码、令牌、密钥和声明为敏感的字段必须脱敏；`byte[]`、`char[]`、LOB 和无法控制大小的对象不打印正文；单值和
  整条消息始终受长度上限保护。
- 未开启 DEBUG 时，普通成功 SQL 不进行参数字符串化和整句日志拼装，避免观测功能拖慢热路径。
- 日志出口异常只能被隔离和计数，不能改变数据库执行结果。
- core/rdb 继续使用框架无关 observer/日志出口；Spring 示例负责把上层日志级别映射到该能力，其他 Java 生态可用
  自己的日志框架完成同样映射。

## 七、分阶段实施计划

### 阶段 0：V2 基线与版本准备

- [x] 将 Maven 开发版本切换到 V2，并在发版收口阶段固定为 `2.0.0`；V1.0.1 标签和认证证据保持不变。
- [x] 保存 V1.0.1 的公开 API、SQL/参数、事务、批量、错误、性能和真实库基线。
- [x] 建立 JDBC/R2DBC 能力矩阵和同请求双执行契约，不重新发明已有功能。
- [x] 盘点受影响生产类规模，确认本阶段不会产生新的大型类。

阶段 0 的证据索引、双执行矩阵、等价性判定和大类门禁见
[`v2.0.0-execution-contract.md`](v2.0.0-execution-contract.md)。V1 真实库结果只作为回归参照，V2 当前代码仍要在最终阶段
重新认证。

### 阶段 1：抽取执行方式无关契约

- [x] 让 SQL 请求、行读取目标、更新结果、执行保护、错误和 observer 不依赖具体驱动类型。
- [x] 保留 R2DBC 真响应式接口，建立清晰的同步执行接口；不使用一个含糊接口混装阻塞和响应式方法。
- [x] 删除 `SyncSqlExecutor.bridge(...)`、R2DBC 阻塞同步 executor 及其内部装配分支；同步入口已经迁移到原生 JDBC。
- [x] 让 FormClient、Repository、Operator 和 Schema 只依赖对应执行能力，不直接持有连接工厂。
- [x] 用契约测试锁定 SQL、参数顺序、Scope、安全和结果语义，V1 结果只作为回归参照而不是兼容包袱。

### 阶段 2：真正的 JDBC 执行器

- [x] 接入 `DataSource` 和外部/自有 `Connection` 生命周期。
- [x] 实现 PreparedStatement 参数绑定、查询、更新、生成键和 ResultSet 流式读取。
- [x] 对齐 timeout、fetch size、max rows、线程中断取消、LOB 限制和资源关闭。
- [x] 复用 codec、DynamicRow、实体映射、错误分类和执行 observer。
- [x] 保证同步 JDBC 热路径不经过 Reactor，且没有无界中间集合。

阶段 1、2 当前说明：原生 JDBC 单条查询、更新和生成键已经接入，旧 R2DBC 阻塞同步桥已经删除。执行保护已覆盖
JDBC query timeout、fetch size、最大行数、结果内存、LOB 和资源关闭；取消遵循执行契约，在发 SQL 前和逐行读取时
检查调用线程中断并尽力调用 `Statement.cancel()`。外部事务连接复用与所有权也已经落地。

### 阶段 3：统一启动、方言与动态数据源

- [x] 统一接收 `DataSource`、`ConnectionFactory` 或两者，并按能力装配执行器。
- [x] 实现显式方言优先以及 JDBC/R2DBC metadata 自动识别。
- [x] 同时存在两套连接能力时验证方言一致，动态物理库可通过统一 Builder 在启动期完成全量方言校验。
- [x] 路由在事务前确定，事务中锁定物理库，读写路由遵守事务读主库规则；纯 Java 接入示例明确由主库事务连接固定路由。
- [x] 业务代码不需要手动组装 executor、renderer 或 dialect。

### 阶段 4：统一 CRUD、动态表单与 DDL/DML

- [x] FormClient、Repository、DatabaseOperator、Schema、Metadata 和原生 SQL 已接入两种执行方式。
- [x] 实体 Lambda、结构化条件、自定义 term、Scope、逻辑删除和乐观锁保持同一调用方式。
- [x] JDBC 与 R2DBC 对同一方言共享 SQL 渲染、参数顺序和结果语义。
- [x] 动态查询继续默认返回紧凑 `DynamicRow`，JDBC 读取不先物化普通 Map。
- [x] 引入 flying-orm 自有 `@TableName`、`@TableId`、`@TableField`、`@Version`、`@TableLogic`、
  `@EnumValue`、`@KeySequence` 和对应策略枚举，移除 V2 对 Jakarta Persistence 实体注解的读取路径。
- [x] `AUTO`、数据库序列单条和批量 insert 都通过同一连接取得生成键并安全回填可变实体；批量按输入偏移逐行
  交付主键，不在结果对象中积压整批键。`ASSIGN_ID`、`ASSIGN_UUID` 已覆盖 JDBC/R2DBC 单条和批量写入；数据库
  生成主键的批量 upsert 因缺少明确冲突身份，会在消费输入和执行 SQL 前拒绝。
- [x] 增加框架无关 `IdGenerator` SPI 和显式雪花生成器；worker/node id 未可靠配置时 SQL 前失败。
- [x] 让 `TableField.select/fill`、前端投影、FieldScope、单条和批量写入遵守同一字段策略。
- [x] 用 `@EnumValue` 完成枚举成员值映射，缓存访问计划并校验数据库值唯一性。

## 八、完成标准

V2.0.0 只有同时满足以下条件才算完成：

- 同一业务代码可以选择 JDBC 同步运行或 R2DBC 响应式运行，无需重写 DSL、实体、动态表单和安全规则。
- 响应式链路没有 JDBC、`block()` 或阻塞式数据库访问；JDBC 链路没有无意义 Reactor 包装。
- V2 生产代码中不存在 R2DBC 阻塞同步桥接，也不存在让同步调用自动退回 R2DBC 的配置或工厂入口。
- 上层事务能够完整控制连接和最终提交结果，不出现双重提交、提前 `COMMITTED` 或连接误关闭。
- 普通接入不要求业务代码组装内部对象；显式方言和自动识别都具备清晰的失败边界。
- 主键生成、字段填充、查询排除和枚举值映射在 JDBC/R2DBC、单条/批量、实体/动态表单边界上行为一致。
- 雪花 ID 只能显式开启且具备节点和时钟安全校验；数据库生成主键可以被可靠返回，不停留在 DDL 声明层。
- DEBUG 能直接看到安全 SQL、参数、耗时与结果；慢 SQL 和故障即使未开 DEBUG 也留下安全证据。
- JDBC/R2DBC 通过同一套功能契约；H2 嵌入式契约、MySQL/PostgreSQL/SQL Server 的真实认证、Oracle 的条件认证，以及发布要求内的并发稳定性和性能门禁已经完成。
- core/rdb 保持零 Spring 依赖、少模块结构和大型类门禁。
