# 真实连接池与响应式并发稳定性设计

## 目标

在固定 Docker MySQL/PostgreSQL 上验证三类容易把线上服务拖垮的资源边界：连接池接近耗尽时的等待超时与恢复、慢消费者只按需求取数并中途取消、持续有界并发结束后连接全部归还。测试要能稳定复跑，指标口径要说清楚，不把驱动内部预取误写成已经验证的零缓存。

## 方案比较

### 方案一：只用假的 ConnectionFactory

执行快，也容易精确控制信号，但现有单元测试已经覆盖连接永不返回、取消和超时映射。它不能证明真实连接池是否收到取消、连接是否归还，更不能发现驱动在取消结果流时的资源释放差异。

### 方案二：使用业务默认大连接池做高压力长跑

场景接近生产，但结果很容易受本机 CPU、Docker 资源和其他进程影响。长跑适合下一批正式性能认证，不适合用来判断一个确定的资源契约是否正确。

### 方案三：真实数据库加固定小连接池

本批采用这个方案。每个场景自己创建最多 2 或 4 条连接的小池：主动占满连接制造确定性等待，使用下游逐步 request 和 cancel 验证响应式边界，再用现有 `ReactiveConcurrencyProbe` 运行有限次数的持续并发。池指标只记录已分配、已借出、空闲和等待数，不记录连接串或 SQL 参数。

## 认证结构

新增 `ExternalR2dbcConcurrencyStabilityCompatibilityTest`，继续读取现有 MySQL/PostgreSQL 系统属性。未配置 URL 时安静跳过，日常 `mvn test` 不需要 Docker。

每个数据库执行三类场景：

1. 创建最大容量为 2 的连接池并借走两条连接。第三个 ORM 查询设置更短的 `connectionAcquireTimeout`，必须得到 `RdbConnectionAcquireTimeoutException`；归还连接后等待队列必须清空，轻查询必须成功。
2. 准备一批有序数据，订阅查询时初始请求量为 0，再分段请求少量记录并取消。测试只证明 flying-orm 返回的 Publisher 遵守下游 demand、取消会传到连接使用边界，而且同一个池随后还能执行查询；不承诺驱动内部完全没有预取。
3. 使用最大容量为 4 的池和 `ReactiveConcurrencyProbe` 连续执行有限次查询，并发上限与池容量一致。全部操作必须完成，探针峰值不能越界，结束后池的借出数和等待数必须回到 0。

## 依赖与边界

- `r2dbc-pool` 只放在 testkit 的测试依赖中，不进入 ORM 运行时，也不替上层决定连接池实现。
- 本批不新增公共 API，不创建线程池，不加入 Spring。
- 测试表使用固定名称，执行前后清理。连接和连接池都在 `finally` 或响应式资源边界中关闭。
- 连接获取超时由 `SqlExecutionOptions` 控制，连接池自己的超时设置得更长，用来确认异常来自 flying-orm 的统一保护层。
- 慢消费者测试不靠 `Thread.sleep` 阻塞驱动事件循环；由 `StepVerifier` 控制 request 和 cancel。
- 持续并发是稳定性认证，不输出吞吐或 P95/P99 结论；这些数字留给下一批固定资源性能长跑。

## 通过条件

- MySQL/PostgreSQL 都能稳定复现连接池满，得到统一连接获取超时，并在释放后恢复。
- 两库查询都不会在下游没有 demand 时向订阅者推送记录；取消后池无借出和等待，后续查询成功。
- 两库持续并发全部成功、无整体超时、峰值不超过配置，并在结束后回到零借出、零等待。
- 普通 Maven 回归全绿，Core 认证无失败，证据目录不含凭据。
