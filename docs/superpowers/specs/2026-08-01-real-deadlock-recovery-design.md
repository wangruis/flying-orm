# 真实死锁、连接中断与 UNKNOWN 恢复设计

## 目标

在固定 Docker MySQL/PostgreSQL 上继续验证三类高风险故障：真实死锁、正在执行 SQL 时连接被数据库终止，以及事务已经提交但调用方没有拿到提交确认。认证必须能稳定复跑，并且只声明数据库和驱动真正参与过的行为。

## 方案比较

### 方案一：只使用 testkit 故障注入

速度最快，也最稳定，但只能证明上层状态机如何处理预设异常，不能证明数据库错误码、驱动连接状态和事务释放行为。现有单元测试已经覆盖这一层，本批不重复把它包装成真实库结论。

### 方案二：重启容器或临时断开 Docker 网络

故障最接近机器宕机和网络分区，但时间点很难控制。容器恢复时间还会把单个测试拖到几十秒，并容易让同批其他场景受到影响。它适合后续长时间容灾演练，不适合当前需要稳定复跑的阻断测试。

### 方案三：数据库会话控制加提交确认丢失边界

本批采用这个方案。死锁由两个真实事务反向持有两行锁产生；连接中断由独立管理连接调用数据库原生命令终止慢查询会话；提交结果未知则让真实提交先完成，再关闭该连接并向执行器返回连接异常。第三种场景的断点位于提交确认边界，不伪造业务数据或回执，因此可以真实验证回执查询和幂等重放。

## 认证结构

新增 `ExternalR2dbcFailureRecoveryCompatibilityTest`，继续读取现有 MySQL/PostgreSQL 系统属性。没有配置 URL 时全部测试安静跳过，普通 `mvn test` 不要求 Docker。

每个数据库各执行三类场景：

1. 两条连接各自开启事务，先分别锁住不同记录，再同时申请对方持有的记录。数据库必须选择一个死锁受害者，原始驱动异常经 `RdbExceptionTranslator` 后必须稳定归类为 `DEADLOCK`。两条连接在成功和失败路径都回滚并关闭。
2. 受测连接先读取自己的数据库会话编号，再通过 `R2dbcSqlExecutor` 执行慢查询。管理连接稍后终止该会话，执行器必须返回 `CONNECTION`；随后使用正常连接执行 `select 1`，确认数据库服务和执行入口仍可继续工作。
3. ATOMIC 回执批量在真实事务中同时写入业务数据和回执。包装连接在真实 `commitTransaction()` 完成后立即关闭连接并返回 SQLState `08006`，执行器必须报告带恢复令牌的 `UNKNOWN`。稳定执行器随后把令牌解析为 `COMMITTED`，用相同操作编号重放时直接读取回执，不能重复写入业务数据。

## 边界与安全

- 不重启容器，不修改 Docker 网络，不影响同批其他数据库。
- 管理 SQL 只使用刚从受测连接读取的数字会话编号，不接收外部字符串。
- 测试表和回执表使用固定名称，执行前后都清理；清理失败不能掩盖主场景失败。
- 不新增公共 API。真实测试若暴露错误码或状态机缺口，先补最小失败契约，再修改生产代码。
- 主项目继续零 Spring 依赖，认证证据继续写入被忽略的 `target/certification-results`。

## 通过条件

- MySQL/PostgreSQL 各产生一次真实死锁，并稳定得到 `DEADLOCK`。
- 两库各有一个慢查询会话被真实终止，执行器得到 `CONNECTION`，随后轻查询成功。
- 两库各产生一次带恢复令牌的 `UNKNOWN`，恢复结果为 `COMMITTED`，重放后业务表仍只有原始两行。
- `mvn test` 全绿；`Core` 认证无失败，Oracle/SQL Server 未启动场景仍按设计跳过。
