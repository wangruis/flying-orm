# flying-orm v1.0.0 全面收敛设计

## 1. 目标

在不保留历史兼容包袱的前提下，把 flying-orm v1.0.0 一次收敛到正式发布形态。

所有取舍按以下顺序裁决：

1. 简单易用；
2. 稳定与安全优先；
3. 高性能；
4. 低延迟；
5. 高吞吐。

本次不是兼容性补丁。项目仍是新项目，因此删除错误、重复、模糊或容易误用的公共 API，直接形成清晰的 v1.0.0 契约。

## 2. 全局约束

- JDK 21。
- flying-orm 本体只包含纯 Java、Reactor、R2DBC 能力，不依赖 Spring，也不提供 Spring Boot Starter。
- Spring 自动扫描、Bean 注册、继承式 Service 和启动生命周期编排只属于上层服务或仓库外的独立适配项目。
- 不使用 ThreadLocal 保存响应式业务上下文。
- 默认行为安全有界；危险能力必须显式命名和显式开启。
- SQL 业务值必须参数绑定，动态标识符必须经过方言引用和标识符校验。
- update、delete、物理删除必须保留非空条件保护。
- 租户、DataScope、逻辑删除和乐观锁继续 fail-closed。
- 缓存不得保存租户值、参数值、请求上下文、实体实例或可变条件树。
- 性能优化必须同时有正确性测试、内存边界和基准证据。
- 本次保持项目版本为 `1.0.0`。

## 3. 实施批次

整个设计作为一个 v1.0.0 交付，但按三个可独立验证的批次实施：

1. 正确性与安全；
2. 缓存与性能；
3. 公共 API 与工程质量。

每个批次都采用测试先行，完成后运行对应模块测试和全量回归。全部完成后再执行三轮独立深度自查，每轮发现的确定性问题继续通过失败测试和最小修复闭环。

## 4. 正确性与安全

### 4.1 普通 SQL 安全默认值

新增并默认使用 `SqlExecutionOptions.safeDefaults()`：

| 项目 | 默认值 |
| --- | ---: |
| SQL 总超时 | 30 秒 |
| 查询最大返回行数 | 100,000 |
| 单个二进制 LOB 最大物化量 | 16 MiB |
| 单个文本 LOB 最大物化量 | 16,000,000 字符 |
| 获取连接最大等待时间 | 5 秒 |

`SqlExecutionOptions.unlimited()` 保留，但只能由调用方显式选择。`FlyingOrmClients`、`R2dbcSqlExecutor`、FormClient 和 Repository 的默认组装全部使用安全默认值。

### 4.2 DDL 安全默认值

DDL 使用独立的默认执行保护：

| 项目 | 默认值 |
| --- | ---: |
| 单条 DDL 超时 | 60 秒 |
| 获取连接最大等待时间 | 10 秒 |
| 元数据锁或表锁等待 | 10 秒 |

删列、改类型、改主键、索引重建和其他存在回滚缺口的动作继续要求：

- 先生成审核计划；
- 计算稳定指纹；
- 使用与当前指纹完全一致的批准对象；
- 记录批准原因。

### 4.3 原生 SQL 危险入口

- 删除 `nativeSql(...)`。
- 只保留 `unsafeNativeSql(...)`。
- 类型和方法 Javadoc 必须明确说明：不会自动应用租户、DataScope、逻辑删除和乐观锁。
- 继续强制单语句、命名参数完整匹配、参数绑定和动态标识符白名单。
- 原生 SQL 入口必须同样继承默认超时、行数、LOB 和连接获取限制。

### 4.4 连接清理与提交事实

当前 Reactor `usingWhen` 会在异步 cleanup 失败时用 cleanup 错误覆盖成功终止信号。该行为不能直接用于已经完成写入或已经提交事务的结果语义。

新规则：

- SQL 结果已经完整取得后，连接 `close/reset` 失败不能把成功结果改写成失败。
- 事务 `commitTransaction()` 已成功后，后续关闭失败不能返回失败或 UNKNOWN。
- 提交调用本身失败或超时时，继续返回 UNKNOWN，并携带恢复依据。
- cleanup 失败必须进入独立资源清理观测，不允许静默丢失。
- 路由连接 reset 失败时必须关闭并丢弃物理连接，不能回池复用。
- cleanup 失败不得触发业务层自动重试语义。
- SQL/DDL/批量业务超时只覆盖数据库操作，不覆盖已经确认结果后的资源清理。
- cleanup 使用独立、严格有界的超时；失败或超时只进入资源清理观测，不能改变已经确认的业务结果。
- 租户 schema/RLS reset 失败必须通过显式连接失效契约淘汰底层池连接；普通 `close()` 不得冒充物理淘汰。

执行观测需要区分：

- 业务执行状态；
- 提交状态；
- cleanup 状态。

### 4.5 DDL 后的缓存一致性

DDL 计划一旦开始执行，目标表元数据可能已经变化。因此：

- 全部成功：失效目标表元数据和关联结构计划。
- 中途失败：失效目标表元数据和关联结构计划。
- session cleanup 失败：失效目标表元数据和关联结构计划。
- 取消或超时：保守失效目标表元数据和关联结构计划。
- 审批失败、计划为空或尚未开始执行：不失效。

失效动作必须幂等，并且不能覆盖原始 DDL 结果或异常。

### 4.6 批量回执完整性

批量回执是 UNKNOWN 恢复的事实来源，必须采用严格基数和行数校验：

- reserve 必须恰好影响一行；
- complete 必须恰好影响一行；
- 查询只能返回零行或唯一一行；
- 多行回执视为数据完整性错误；
- 回执缺失只能得到 UNKNOWN；
- plan hash、payload hash、row count、affected rows 必须精确匹配；
- 数值溢出和小数继续明确拒绝；
- 回执表名继续限制为安全的 `table` 或 `schema.table` 标识符。

## 5. 统一缓存治理

### 5.1 统一策略语义

元数据、SQL 结构计划、条件结构计划和实体映射全部真实支持：

- `enabled`；
- `maximumWeight`；
- `maximumEntryWeight`；
- `expireAfterAccess`；
- `recordStats`；
- oversized 拒绝计数；
- 精确失效；
- 全量失效；
- 命中、未命中、加载成功、加载失败、淘汰和权重快照。

不得再把 `maximumWeight` 转换为 `maximumSize`，不得把 `expireAfterAccess` 降级为 `expireAfterWrite`，不得忽略 `maximumEntryWeight` 或 `recordStats`。

### 5.2 元数据缓存

- `DynamicForm` 权重由基础成本、字段、主键、租户、逻辑删除和版本信息组成。
- `TableMetadata` 权重由基础成本、字段、索引、外键和约束组成。
- 同一个 key 的并发 miss 只允许一次底层加载。
- 加载异常不得长期缓存，失败后立即允许重试。
- `table` 失效清除所有 schema 下同名表；`schema.table` 只清除精确目标。

### 5.3 实体模型与映射计划缓存

- 删除固定每实体 64 个 codec registry 的静态策略。
- 缓存改为 `FlyingOrmClients` 实例持有并由 `OrmCachePolicy.entityMappings()` 控制。
- EntityMetadata、EntityValues 和 MappingPlan 统一由实例级实体模型注册表管理。
- Repository、FormClient 和 unsafe native SQL 类型映射共享同一注册表。
- 缓存必须有界、可统计、可关闭，并避免长期阻止类加载器回收。

### 5.4 真正的 SQL 结构计划

删除把完整 SQL 字符串同时作为 key 和 value 的驻留实现。

结构计划至少包含：

- 参数化 SQL；
- 参数槽布局；
- 投影列布局；
- 操作类型；
- 方言和 bind marker 信息；
- 与表单结构指纹的关联。

缓存键只包含：

- 方言；
- 表单结构指纹；
- 操作类型；
- 字段集合；
- 条件形状；
- 分页和排序形状。

缓存命中后只提取本次参数，不重新拼接完整 SQL。条件值、租户值、DataScope 值、分页数值和实体实例不得进入缓存键或缓存值。

DDL 失效必须同时清除受影响表的 SQL 结构计划。结构指纹变化不能误命中旧计划。

### 5.5 性能验收

每个缓存区域必须覆盖：

- 并发单次加载；
- 命中和未命中；
- 权重淘汰；
- 单条 oversized 旁路；
- TTL；
- 精确失效；
- 关闭缓存；
- 加载失败恢复；
- 跨租户不串值。

SQL 计划优化必须通过 JMH 或现有基准框架证明：

- 热路径分配量下降；
- 相同结构查询延迟不回退；
- 高并发吞吐不回退；
- 缓存关闭时结果完全一致。

## 6. 公共 API 收敛

### 6.1 原则

- 不保持旧 API 兼容。
- 常用 CRUD 保留最短调用路径。
- 高级参数集中到不可变规格对象，不通过重载矩阵表达。
- Reactive 与 Sync 共享同一组请求模型。
- 公共门面少而完整，内部实现默认包级可见。

### 6.2 FormClient

`ReactiveFormClient` 只保留：

- 常用 insert、select、update、delete、page；
- 接收不可变 QuerySpec、WriteSpec、BatchSpec 的高级入口；
- 创建 Repository 的入口；
- 必要的默认配置派生方法。

内部拆分为查询、写入、分页、批量、Scope 合并和结果映射组件。同步客户端只桥接同一规格对象，不复制全部组合重载。

### 6.3 Repository 与 Operator

- Repository 聚焦实体 CRUD、实体元数据、逻辑删除和乐观锁。
- DatabaseOperator 聚焦表名驱动的 DDL、DML、查询和 unsafe native SQL。
- 原 v1.0.2 Lambda-first 实体 API 已整体前移到 v1.0.0，必须覆盖查询、投影、排序、分组、更新、
  原子增减、删除和乐观锁，并共享同一份实体元数据与字段解析缓存。
- FormClient、Repository、Operator 不互相复制相同能力。

### 6.4 批量写入

`R2dbcBatchWriter` 拆分为：

- 分片和内存预算；
- 驱动批处理执行；
- 事务状态机；
- 回执存储和恢复；
- 结果汇总。

对外继续只有统一批量请求模型。默认流式有界，ATOMIC 与 INDEPENDENT 的事务和 UNKNOWN 语义保持清晰。

## 7. 工程质量门禁

### 7.1 公共 API 门禁

自动检查：

- 公开类型和方法白名单；
- 内部实现类不得意外 public；
- 重复工厂和重复重载不得重新出现；
- 危险入口必须带 `unsafe`；
- Reactive 和 Sync 的规格对象保持一致。

### 7.2 构建门禁

- JaCoCo：为 core 和 rdb 设置可执行的行覆盖、分支覆盖阈值。
- SpotBugs：阻止高优先级缺陷。
- Checkstyle：检查基础格式和项目 Javadoc 规则。
- Maven Enforcer：继续检查 Java、Maven 和依赖收敛。
- dependency analyze：发布 profile 阻止未声明和无用直接依赖。
- OWASP dependency-check：发布安全 profile 阻止 CVSS 7.0 及以上漏洞，并且扫描失败不能静默通过。

门禁阈值以当前真实基线起步，必须能在仓库内稳定复现；后续只能提高，不能无说明降低。

### 7.3 多数据库验证

- 普通 `mvn verify`：运行单元测试、H2 集成测试和模拟驱动测试，不依赖外部服务。
- `real-db` profile：MySQL、PostgreSQL；profile 激活后缺少配置直接失败，不能 skip。
- `preview-db` profile：Oracle、SQL Server；profile 激活后缺少配置直接失败，不能 skip。
- 正式发布流程必须通过 `real-db`。
- Oracle、SQL Server 继续按 V1 预览支持管理，认证结果单独记录。

### 7.4 注释与文档

- 所有公开类型、构造器、公开方法和测试类型补齐中文说明。
- 类型级 Javadoc 包含 `@author wangr`、创建或调整日期、`@version v1.0`。
- 更新需求索引、能力矩阵、v1 路线图、缓存设计、安全默认值和发布说明。
- 删除与实现不一致的“已完成”描述。

## 7A. 上层框架与 Schema 治理的最终边界

- flying-orm 只提供与框架无关的实体元数据、结构计划、风险分类、审批和执行 API，不感知 Spring 启动生命周期。
- 上层 Spring 服务如需启动期同步，默认模式、扫描范围、迁移锁、就绪门禁和配置绑定均由上层自行实现。
- `PLAN` 必须生成可消费的结构化报告，至少包含实体、物理表、步骤、风险、阻塞原因和指纹。
- `REVIEWED` 使用“物理表 -> 批准指纹与原因”的映射，不允许一个全局指纹冒充多表批准。
- 实体模型生成的目标结构必须保留 nullable、unique、索引和约束；危险变化继续进入人工审核。
- 支持实体级排除自动 DDL，但不影响该实体 Repository 的注册和使用。
- Oracle advisory lock ID 必须在 `0..1_073_741_823` 内，各方言锁 SQL 必须有契约测试。
- Schema 操作完成后进行最终复核；已开始的 DDL 无论成功、失败、取消或 cleanup 失败都保守失效缓存。

## 7B. 查询、缓存和批量的最终正确性契约

- 游标分页必须验证最后排序字段唯一且所有游标字段不可空；若调用方未提供唯一尾键，由实体入口自动追加主键。
- SQL 计划缓存键不得包含完整 SQL 或参数值；计划命中不得重新遍历条件树和拼接完整 SQL。
- 不带 schema 的表失效必须清除所有 schema 下同名表的元数据和 SQL 计划。
- 算术更新只接受规范化的数值类型集合，禁止用 `contains("INT")` 等模糊判断。
- `UpdateDelta` 在 insert、upsert 和批量任意一行都必须在调用驱动前拒绝。
- 批量取消时 rollback 失败必须观测为未确认结果，并使连接进入失效流程，不能静默吞掉。

## 8. 测试策略

所有行为修改遵循 RED-GREEN-REFACTOR：

1. 写最小失败测试；
2. 运行并确认因目标行为缺失而失败；
3. 写最小实现；
4. 运行聚焦测试；
5. 运行模块测试；
6. 运行全量测试；
7. 只在全绿后重构。

重点故障注入场景：

- SQL 成功后 close 失败；
- commit 成功后 close 失败；
- commit acknowledgement 丢失；
- DDL 部分成功后失败；
- DDL 成功但 session cleanup 失败；
- DDL 执行中取消；
- 回执 reserve/complete 返回 0、2 或多 Result；
- 回执查询重复行；
- 缓存并发 miss、加载失败、oversized、TTL 和精确失效；
- SQL 结构相同但租户值、条件值不同；
- 大批量上游取消、超限和连接池耗尽。

## 9. 三轮最终深度自查

全部实施完成后执行三轮相互独立的自查和修复。

### 第一轮：正确性与安全

- SQL 注入和标识符边界；
- 租户、DataScope、逻辑删除和乐观锁；
- 事务状态、提交事实、UNKNOWN、回执恢复；
- DDL 审批、部分执行和缓存一致性；
- 异常翻译和敏感信息。

### 第二轮：并发、内存与性能

- Reactor 取消和 cleanup；
- 连接池、超时和背压；
- 缓存并发、权重、TTL 和类加载器引用；
- 批量分片和结果上限；
- 分配量、延迟和吞吐基准。

### 第三轮：API 与发布

- 公共 API 数量、职责和命名；
- 模块依赖方向和无用依赖；
- Javadoc、需求和能力矩阵一致性；
- 本地、真实数据库和发布 profile；
- 全量构建、静态分析和安全审计。

每轮发现确定性问题后，继续补失败测试、修复、运行聚焦测试和全量验证。三轮结束后才形成最终交付结论。

## 10. 完成标准

- 上述高、中、低优先级问题全部关闭。
- 新发现的提交/close、DDL 缓存和回执完整性问题全部关闭。
- 所有缓存策略真实生效且有可观测快照。
- 默认执行有安全边界，显式 unlimited 仍可用。
- 公共 API 已收敛，没有兼容别名和半废弃入口。
- 普通 verify、质量门禁和发布 profile 行为清晰。
- 三轮深度自查和对应修复完成。
- 工作区不存在非预期文件修改，`git diff --check` 通过。
