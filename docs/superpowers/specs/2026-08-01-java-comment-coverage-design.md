# Java 中文注释治理设计

## 目标

让维护者只看类和方法注释，就能先理解 flying-orm 的职责边界、调用方式、事务与并发语义、安全约束和失败结果，再决定是否需要阅读实现细节。

本任务只补充和整理注释，不改变 API、SQL、事务、缓存、并发或异常行为。

## 范围

- 处理 `flying-orm-core` 和 `flying-orm-rdb` 下的生产 Java 源码。
- 处理上述两个模块的测试 Java 源码。
- `flying-orm-testkit` 和 `flying-orm-benchmark` 维持现状。
- 测试目录中的 Jakarta/Javax 注解替身只说明测试用途，不扩写成正式 API 文档。
- 不修改用户本地的 `AGENTS.md`。

## 注释层级

### 类型

每个类、接口、枚举、注解和 record 都要说明：

- 它负责什么。
- 它不负责什么，尤其是事务、权限和数据库差异的边界。
- 它通常由谁创建、在哪里使用。
- 存在线程安全、不可变性或生命周期要求时，明确写出来。

### 公共 API

所有 `public` 和 `protected` API 应说明：

- 方法完成的业务动作。
- 参数允许什么，不允许什么。
- 返回值代表完成、失败、部分成功还是未知状态。
- 会主动抛出的异常和调用方需要处理的边界。
- JDBC 桥接、R2DBC 非阻塞、批量事务或 Scope 合并等容易误解的语义。

简单 getter、record 自动访问器和没有额外语义的枚举读取方法不重复解释字段名称。

### 内部实现

复杂私有方法和代码块重点解释“为什么”：

- SQL 注入防护和结构化条件校验为什么放在这里。
- 总超时、取消、回滚和 `UNKNOWN` 如何区分。
- 缓存键、失效时机和并发可见性如何保证。
- 参数顺序、方言渲染和批量分片为什么必须保持一致。

不为普通赋值、集合遍历、空值判断或显而易见的转发方法添加逐行旁白。

### 测试

测试代码采用轻量注释。测试类只需说明覆盖的能力边界；复杂或高风险用例说明它要防止的具体回归，例如 OR 绕过 Scope、事务未启动却回滚、超时预算重置或 DDL 类型注入。普通断言、测试数据准备和名称已经足够清楚的测试方法不再扩写。

## 注释风格

- 使用自然、直接的中文，先说结论，再补原因。
- 保留必要的英文技术词，如 R2DBC、AST、Scope、SQLState 和 `UNKNOWN`。
- 不使用官样套话，不重复类名或方法名。
- 注释必须与当前实现一致；无法从代码确认的内容不写成事实。
- 长说明拆成短段落或列表，避免一个 Javadoc 塞入整页文字。

## 执行顺序

1. 扫描两个模块所有 Java 文件，建立缺口清单。
2. 先处理 `core` 的条件、表单、Scope、元数据和 SQL 渲染。
3. 再处理 `rdb` 的执行、批量、表单、Repository、DDL、方言、缓存和映射。
4. 最后补测试场景说明，并统一清理失真、重复和乱码注释。
5. 分模块编译，运行少量纯单元测试和全模块跳测打包。

## 验收标准

- 范围内每个 Java 文件的主类型都有可读中文说明。
- 重要公共 API 和复杂内部流程不需要靠猜测理解。
- 没有新增无用 import、无用变量、行为修改或 Spring 依赖。
- `git diff --check`、两个模块编译和全模块打包通过。
- 真实数据库、并发压力和性能测试不属于本次注释任务。
