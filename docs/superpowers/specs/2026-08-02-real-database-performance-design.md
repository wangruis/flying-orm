# 真实数据库性能长跑设计

## 目标

在固定 Docker MySQL/PostgreSQL、固定连接池和固定并发参数下，测量 flying-orm 真实执行层的查询、更新、ATOMIC 批量和 INDEPENDENT 批量。每轮必须同时留下吞吐、P50/P95/P99、错误率、连接池峰值、进程 CPU 和堆内存，结果能复跑、能解释，也能明确区分“本机基线”和“跨机器性能承诺”。

## 方案比较

### 方案一：把数据库调用直接放进 JMH

JMH 很适合条件编译、SQL 渲染、实体映射这类纯 Java 热路径，但用 JMH 线程阻塞等待异步数据库调用，会把阻塞线程调度混进 R2DBC 结果。它也不方便同时记录连接池等待、错误分类和响应式外层并发，因此继续保留现有 JMH，不用它承载真实数据库长跑。

### 方案二：把性能场景写成 JUnit

实现最少，但测试框架关注通过与失败，不适合稳定保存运行参数、分位值和资源指标。性能波动还可能让普通 `mvn test` 变得不稳定。本方案只用少量单元测试校验指标计算，不用 JUnit 运行长跑。

### 方案三：benchmark 模块内增加独立响应式负载器

本批采用这个方案。负载器直接使用 Reactor、`R2dbcSqlExecutor` 和测试期真实驱动，不创建每请求线程；每个并发 worker 完成一次操作后再发下一次，持续到测量截止时间。连接池和驱动只属于 benchmark 运行环境，不进入 core/rdb 运行时。

## 组成

### ReactiveDatabaseLoadProbe

通用负载探针只负责调度和计量，不知道 SQL 内容：

- 输入预热时长、测量时长、外层并发、每次成功代表的行数和一个返回 `Publisher` 的操作工厂。
- 预热阶段执行同样负载，但不进入正式统计。
- 测量阶段记录每次操作从订阅到完成的纳秒耗时，错误也计入总请求和分类。
- 使用 HDR Histogram 保存延迟分布，避免把每次延迟对象都堆在内存里影响长跑。
- 记录实际完成数、失败数、错误率、ops/s、rows/s、P50/P95/P99 和实际测量时长。

### RealDatabasePerformanceRunner

命令行入口负责环境、数据准备和四类场景：

1. `queryById`：从固定种子表按主键读取一行。
2. `updateById`：在足够大的主键范围内轮转更新，减少无意义的单行热点锁竞争。
3. `atomicBatchInsert`：每次写入固定行数，整个请求使用 ATOMIC 事务。
4. `independentBatchInsert`：相同行数拆成固定小分片并有界并发提交，显式使用 INDEPENDENT。

MySQL/PostgreSQL 使用各自独立测试表，批量 ID 单调递增，避免重复键把性能结果变成异常分类测试。每个数据库使用相同池大小和参数，场景结束后要求借出连接和等待申请都归零。

### PerformanceReport

报告 JSON 不保存 URL、用户名、密码、SQL 参数或业务行。它只记录：

- Git commit、开始结束时间、JDK、OS、CPU 标识、逻辑处理器数。
- 数据库名称、驱动名称、连接池版本和公开运行参数。
- 每个场景的吞吐、分位延迟、错误率、错误类型、峰值连接/等待、CPU 和峰值堆内存。
- 整体状态。任一场景有错误、超时、连接未归还或非有限指标，状态必须失败，进程返回非零。

同时生成一份自然中文 Markdown 摘要，方便人工检查；机器判断仍以 JSON 为准。

## 执行入口

认证目录新增独立性能脚本。脚本复用 `certification/.env` 和 Docker Compose：

1. 启动并等待 MySQL/PostgreSQL 健康。
2. 编译 benchmark 及依赖，分别生成只用于 MySQL/PostgreSQL 的运行时 classpath。
3. 每个数据库各用一个独立 Java 进程启动负载器。这样不需要强行统一两个驱动依赖的 Reactor Netty 版本，也能避免场景互相争抢客户端资源。连接 URL 通过只属于当前脚本和子进程的临时环境变量传入，运行后立即清理，不进入命令行、日志和报告。
4. 把 JSON、Markdown、环境信息和运行日志放入被 Git 忽略的 `target/performance-results/<run-id>`。

脚本提供 `Smoke` 和 `Formal` 两档。Smoke 使用很短的预热和测量，只验证链路；Formal 使用固定的较长参数形成当前本机基线。两档都不能自动宣称跨机器性能保证。

## 默认口径

- 连接池：16。
- 查询/更新外层并发：16。
- 批量外层并发：4。
- 每批：32 行。
- INDEPENDENT：8 行一片，片内并发 4。
- 单次 SQL/连接获取保护：10 秒/3 秒。
- Smoke：每场景预热 1 秒、测量 2 秒。
- Formal：每场景预热 5 秒、测量 15 秒。

Formal 一轮约 160 秒，加上建表、种子数据和构建时间，适合本机重复执行。后续做候选版回归时至少跑三轮，并使用三轮中位数判断趋势。

## 边界

- 不修改 flying-orm 公共 API，不给 core/rdb 增加 benchmark 依赖，不加入 Spring。
- 本批只建立 flying-orm 自身真实数据库基线，不提交与其他项目绑定的对比材料。
- CPU 是负载器 Java 进程的平均使用率；Docker 数据库 CPU 需要宿主级采样，当前报告会明确不包含。
- 峰值堆内存来自 JVM 内存池，不能等同于整个进程 RSS。
- P95/P99 是已经完成的单次 ORM 操作延迟；批量场景同时报告 ops/s 和 rows/s。
- 机器有明显后台负载、Docker 资源设置变化、数据库镜像或驱动升级后，旧结果只能作为历史参考。

## 通过条件

- 两库四类场景全部完成，没有非预期错误、超时或连接泄漏。
- 延迟、吞吐、CPU、堆内存和连接指标都是有限非负值。
- 峰值已借出连接不超过池大小，最终借出数和等待数为 0。
- Smoke、Formal、普通 Maven 回归都能独立复跑；报告和日志不含凭据。
