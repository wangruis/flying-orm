# 2026-08-02 RC 三轮性能门禁

## 结论

本轮在固定 MySQL 8.4.10、PostgreSQL 17.10、16 连接池和同一台开发机上连续完成三轮 Formal 运行。
24 个数据库场景全部零测量错误、零预热错误；每轮结束后连接池借出数和等待数都回到 0。

按三轮中位数与首轮真实库基线比较，8 个场景中 7 个通过。MySQL `updateById` 吞吐只回退 0.90%，
P50 也没有变慢，但 P95 回退 12.61%、P99 回退 48.53%，超过 10% 硬线。因此本次 RC 性能门禁结论是
**阻断**，不能用吞吐稳定或其他场景变快抵消这个结果。

## MySQL 更新长尾

三轮 `updateById` 分别为：

| 轮次 | ops/s | P50 ms | P95 ms | P99 ms | max ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 4,002.68 | 3.854 | 6.140 | 8.880 | 109.117 |
| 2 | 4,086.40 | 3.828 | 5.632 | 8.913 | 26.395 |
| 3 | 3,952.68 | 3.940 | 5.382 | 8.929 | 28.099 |

被测 ORM 的单条 `SqlRequest` 更新路径自初始基线提交后没有代码变化。MySQL 检查时没有脏页、待写、redo 等待、
待 fsync 或事务历史链积压；实例启用了 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1` 和 binlog，
每个自动提交更新都要求 redo 与 binlog 持久化。`performance_schema` 的累计文件等待也主要集中在 redo log 和 binlog，
观察到的单次最大等待约为 89 ms 和 75 ms。这与“吞吐/P50 稳定、P95/P99 变长”的结果一致。

初始真实库基线只有一轮，不能证明当时的 P95/P99 是稳定三轮参考值。当前证据足以排除明显 ORM 路径改动，
但不足以直接放行，所以仍保留阻断结论。

## 排除的运行

在找到认证脚本的选择性停止缺陷前曾运行两组三轮。它们执行时 Oracle 和 SQL Server 预览容器仍在后台，
占用了约 2.5 GiB 内存并产生额外 CPU/I/O，因此只保留作诊断，不参与中位数。脚本现已改为按 `-Database`
精确停止服务；删除数据卷则必须显式使用 `-Database All -RemoveVolumes`。

## 后续验证步骤（已执行）

1. 已在独立、可重建的数据卷上完成三轮短顺序复核和三轮完整顺序复核，没有拿单轮最好值替代中位数。
2. 已对 `updateById` 做单场景受控采样，并按场景记录 redo/binlog 文件等待增量。
3. 全程保持 `innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1`，没有降低持久化等级换取更好数字。
4. 完整顺序中的更新尾延迟仍越过 10% 硬线，因此 V1 RC 性能项继续阻断。

## 单场景专项复核

提交 `811e4be911ce` 增加了受控的数据库和场景选择入口。随后只运行 MySQL `updateById` 三轮 Formal：

| 轮次 | ops/s | P50 ms | P95 ms | P99 ms | max ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| `20260801T190028Z-811e4be911ce-formal` | 4,236.28 | 3.871 | 4.588 | 5.513 | 13.091 |
| `20260801T190157Z-811e4be911ce-formal` | 4,272.05 | 3.830 | 4.559 | 5.464 | 13.386 |
| `20260801T190250Z-811e4be911ce-formal` | 4,553.91 | 3.570 | 4.198 | 5.251 | 13.664 |

三轮中位数为 4,272.05 ops/s、P95 4.559 ms、P99 5.464 ms。相对初始基线，吞吐提高约 5.77%，
P95/P99 分别降低约 8.84%/8.95%；每轮仍是零错误、零借出、零等待。单独更新路径因此没有复现 RC
完整顺序中的尾延迟阻断。

三轮窗口内，`performance_schema` 记录到 binlog 文件等待约 175,302 次、累计约 64.67 秒，平均约
0.369 ms；redo log 文件等待约 394,778 次、累计约 59.43 秒，平均约 0.151 ms。严格持久化确实是
每次自动提交的重要成本，但它没有在这组三轮里把 P95/P99 推过基线。

本机同时运行着不属于本项目的 `tdengine-tsdb` 容器。它没有获得停止授权，所以这组三轮只用于缩小问题范围，
不能替代隔离环境下的新基线，也不能直接解除前面的 RC 阻断。下一步复核同一 JVM 内
`queryById -> updateById` 的顺序结果，并分别记录两个阶段的连接池和文件等待变化；如果顺序运行稳定复现，
再检查场景切换和连接复用，否则把重点转回可重建数据卷与宿主机磁盘抖动。

## 查询后更新顺序复核

提交 `5cb4b5cea32d` 增加了 `QueryThenUpdate` 预设和 MySQL 分阶段文件等待日志。业务查询、更新仍使用应用账号；
`performance_schema` 由只存在于认证子进程环境变量中的独立诊断连接读取，没有扩大业务账号权限，也没有把连接串写进报告。

三轮 Formal 原始证据：

查询阶段三轮都没有 binlog 文件等待，只产生 26、26、31 次极少量 redo 事件。更新阶段才出现主要持久化成本：

## V1 发布后更新提交策略对照

提交 `95511dc686fd` 增加了显式开启的操作阶段诊断和固定的 `transactionalUpdateBatch` 对照场景。
后者在一条连接上开始一个显式事务，顺序更新 8 行并提交一次。它只模拟业务明确允许一组修改共同提交的情况，
不会改变 `updateById` 单条自动提交的默认语义。默认性能路径仍直接使用连接池，不经过阶段计时代理。

三轮 `UpdateComparison + PhaseDiagnostics` Formal 原始证据：

- `20260802T171739Z-95511dc686fd-formal`
- `20260802T171857Z-95511dc686fd-formal`
- `20260802T172017Z-95511dc686fd-formal`

| 场景 | rows/s 中位数 | P50 ms | P95 ms | P99 ms | 获取连接 P99 | 执行及提交 P99 | 归还连接 P99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| updateById | 3,803.18 | 3.998 | 5.890 | 9.593 | 0.230 | 8.806 | 1.129 |
| transactionalUpdateBatch | 13,705.42 | 9.208 | 11.387 | 14.074 | 0.124 | 13.443 | 0.888 |

事务组的整组 P99 比单行 P99 高，因为一次操作确实完成了 8 条更新；它的业务行吞吐约为单条自动提交的
3.60 倍。三轮所有场景均为零业务错误，运行结束后连接池借出和等待都回到 0，没有删掉慢轮或挑最好值。

阶段结果再次表明连接获取不是主要问题，尾延迟主要落在 SQL 执行及持久化提交。项目没有调整
`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1` 等持久化设置。当前可交付的优化结论是：
保持单条更新语义不变；业务本来就允许多行共同成功或失败时，上层可以显式使用小事务组来提高行吞吐，
不能由 ORM 在调用方不知情的情况下自动合并提交。
