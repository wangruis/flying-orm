# 2026-07-23 响应式动态表单批量插入

## 背景

逐行调用插入会重复获取连接、创建 Statement 和解析同一条 SQL，不适合作为高吞吐写入的基础。
这一轮先打通动态表单到 R2DBC 的批量插入主链路，保持 API 简单，也不给不支持批处理的执行器偷偷降级。

## 本次实现

- `BatchWriteRequest` 保存一条 SQL、参数类型、数据流和批量策略；List 便捷输入会先按统一列布局生成独立参数数组。
- 第一行决定本批次的字段布局，后续行允许 Map 顺序不同，但字段集合必须完全一致。
- 字段布局只计算一次，后续行按布局直接组织参数，不重复生成列 SQL。
- `ReactiveFormClient.insertBatch(...)` 把整批数据作为一个请求交给执行器。
- `R2dbcSqlExecutor` 在一个连接和一个 Statement 中绑定多组参数，参数组之间调用 `Statement.add()`。
- 执行器按驱动元数据处理参数标记：H2、MySQL 保留 `?`，PostgreSQL 转成 `$1`、`$2`。
- `SqlRequest` 和 `BatchWriteRequest` 都明确记录参数标记来源；数据库原生 SQL 可选择 `NATIVE`，不会误改 PostgreSQL 的 `?` 运算符。
- 批量某一列出现 `null` 时，会优先使用同列非空值的 Java 类型调用 `bindNull(...)`。
- 所有 R2DBC `Result` 的影响行数会合并为一个总数返回。
- 自定义 `ReactiveSqlExecutor` 如果没有实现批量能力，会直接报错，不会在内部悄悄逐行执行。
- 首行和后续行都会按规范化字段名检查重复键，例如同时传 `id` 和 `ID` 会直接报错。
- `r2dbc-h2` 只放在测试范围，真实内存库已跑通建表、含 `null` 的批量插入、影响行数汇总和查询回读。

## 当前边界

- 当前只做批量插入，不包含 upsert。
- 暂不自动切分超大批次，也没有最大批次配置。
- 暂不封装事务、生成主键回填和失败行定位。
- 如果某一列整批都是 `null`，当前没有足够类型信息，只能退回 `Object.class`；后续需要让参数槽携带字段类型。
- PostgreSQL JSON 的结构化 AST 仍在后续阶段；当前需要原生 `?`、`?|`、`?&` 运算符时可使用 `nativeSql(...)` 明确透传。
- 还没有批量规划与执行基准数据，因此不声明性能提升比例。

## 下一步

下一步加入可配置分批和明确的事务边界，再让参数槽携带字段类型解决整列全空问题；
最后用 JMH/专项压测决定参数布局是否需要进一步压平。
