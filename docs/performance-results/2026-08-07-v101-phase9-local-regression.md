# V1.0.1 阶段 9 本地 JMH 回归

这组基准只测 JVM 内部热路径，不连接数据库。真实吞吐和请求 P95/P99 见同日真实数据库报告。

## 环境与口径

- Oracle JDK 21.0.10，JMH 1.37。
- 单线程、单 fork、3 次 1 秒预热、5 次 1 秒测量，启用 GC profiler。
- 完整结果共 25 个场景：[原始 JSON](2026-08-07-v101-phase9-local-jmh.json)。
- 阶段 1 对比：[自动对比报告](2026-08-07-v101-phase9-phase1-comparison.md)。
- 阶段 2 批量计划对比：[自动对比报告](2026-08-07-v101-phase9-phase2-batch-comparison.md)。

## 结论

阶段 1 的 6 个同口径场景都在门禁内：SQL 热计划命中下降 `0.75%`，无计划缓存渲染提升 `2.59%`，
where 渲染提升 `3.52%`。普通执行保护路径没有可见分配。

首轮阶段 9 测量曾发现 `observedUpdate` 从 `238.705 ns/op` 回退到 `344.761 ns/op`，并从 `744 B/op`
增加到 `1392 B/op`。根因是所有 observer 都被迫解析外部事务来源。修复后只有明确申请事务来源的 observer
才进入事务上下文路径，普通 observer 恢复到 `244.073 ns/op`、`768 B/op`；相对阶段基线仅下降 `2.25%`，
不再构成性能回归。

显式开启结构化 SQL 日志但不执行控制台或文件 I/O 时为 `474.156 ns/op`、`2384 B/op`。这项成本只在
上层开启日志时发生；日志关闭的默认客户端不会创建该 observer。

阶段 2 的短口径批量计划对比中，insert 计划编译和行映射分别提升 `2.67%`、`11.94%`；upsert 计划编译
下降 `5.47%`，行映射下降 `3.32%`。该组只有两次测量，未达到 10% 阻断线，继续保留原始 JSON 供后续复跑。
