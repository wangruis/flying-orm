# V2.0.0 JDBC/R2DBC 双执行契约

这份文件固定 V2 两条执行链共同遵守的契约。JDBC 与 R2DBC 可以使用不同驱动，但条件、安全、SQL、事务结果和
业务入口不能因此分裂。

## 基线证据

| 基线 | 仓库证据 | V2 使用方式 |
| --- | --- | --- |
| 公开 API | `flying-orm-rdb/src/test/resources/api/v2.0.0-public-api.txt` | 锁定当前正式公开边界，避免误暴露内部协作类型 |
| SQL、参数、Scope 与错误 | core/rdb 契约测试 | 同一个请求分别交给 JDBC、R2DBC，比较 SQL、参数顺序和结果 |
| 事务与批量 | 批量及事务契约测试 | 锁定 ATOMIC、INDEPENDENT、ENLISTED、UNKNOWN 和恢复语义 |
| 性能与分配 | `flying-orm-benchmark` 与 `docs/performance-results` | 使用相同 JDK、参数和场景做回归，不拿不同环境数字硬比 |
| 真实数据库 | `docs/database-certification-2026-08-08-v2.0.0.md` | 使用当前代码认证，旧结果不能冒充当前结论 |

## 双执行能力矩阵

| 能力 | JDBC 同步执行 | R2DBC 响应式执行 | 必须共享的契约 |
| --- | --- | --- | --- |
| 连接入口 | `DataSource` | `ConnectionFactory` | 显式方言优先，未配置时自动识别 |
| 普通查询与写入 | 原生 JDBC，当前线程阻塞 | 原生 R2DBC，端到端非阻塞 | 同一 SQL 请求、参数顺序、结果和错误分类 |
| 动态表单与实体 | 同步 FormClient/Repository/Operator | 响应式 FormClient/Repository/Operator | 同一元数据、条件、Scope、codec 和字段策略 |
| 批量写入 | `PreparedStatement` 有界分片 | R2DBC 有界分片 | 默认 ATOMIC、显式 INDEPENDENT、统一结果与恢复状态 |
| 外部事务 | 复用上层绑定的 JDBC `Connection` | 复用上层绑定的 R2DBC `Connection` | ORM 不提交、回滚或关闭外部连接 |
| 自管事务 | JDBC 连接本地事务 | R2DBC 连接本地事务 | 只有最终状态确定后才能报告 COMMITTED |
| Schema 与元数据 | JDBC metadata 和 JDBC DDL | R2DBC metadata 和 R2DBC DDL | 同一差异计划、风险审核和缓存失效 |
| 原生 SQL | 参数化 JDBC 执行 | 参数化 R2DBC 执行 | 禁止字符串拼值，复用执行保护和 observer |
| 资源保护 | timeout、fetch size、max rows、取消、LOB 上限 | timeout、背压、max rows、取消、LOB 上限 | 失败可分类，资源必须归还，日志不能改变结果 |
| 执行观测 | 事件标记 `JDBC` | 事件标记 `R2DBC` | 使用同一事件结构、事务来源、结果类型和失败分类 |

## 等价性判定

1. 两条执行链收到相同的表单、实体、条件、Scope 和方言时，渲染出的 SQL 文本与参数顺序必须一致。
2. 数据库驱动返回形式可以不同，但进入公开结果前必须转换成相同的 `DynamicRow`、影响行数、生成键和错误分类。
3. 同步 API 不创建 Reactor 对象，响应式 API 不调用 JDBC，也不允许用线程池包装 JDBC 冒充响应式。
4. 外部事务期间，连接所有权始终属于上层；ORM 只能执行 SQL 和报告 `ENLISTED`，不能提前报告提交成功。
5. JDBC 特有的滚动结果集、保存点和完整 metadata 只能通过显式高级入口使用，不能污染普通 CRUD。
6. flying-orm 不复制上层事务管理器的 begin/commit/rollback 日志体系。普通执行事件携带事务来源，外部事务批量通过
   `ENLISTED` 和完成通知表达最终结果，既可观测，也不会形成第二套事务控制面。
7. 批量 `Publisher<Object[]>` 的每次信号都按当时内容快照；上游复用数组不能改变已接收行，JDBC/R2DBC 的数组所有权语义一致。
8. 驱动和事务内回调的异常都必须经过事务与资源清理；自有事务回滚无法确认时统一报告 `UNKNOWN` 并隔离连接。

## JDBC 驱动差异边界

这些差异由 JDBC SPI 和具体驱动决定，flying-orm 只做能够稳定证明的转换，不根据数据库名称伪造能力：

| 能力 | flying-orm 的统一处理 | 驱动不能提供时 |
| --- | --- | --- |
| 单条生成键 | 使用 `Statement.RETURN_GENERATED_KEYS`，读取后转换为与 R2DBC 相同的 `DynamicRow` 结果 | 返回空生成键集合；需要生成键回填的实体写入会按自己的主键契约失败，不能拿影响行数冒充主键 |
| 批量影响行数 | 普通批量汇总驱动给出的确定行数；乐观锁 `EXACTLY_ONE` 要求每一项都明确等于 1 | `SUCCESS_NO_INFO`、返回项数不足或 `EXECUTE_FAILED` 不能证明逐行结果，按结构化批量失败或 `UNKNOWN` 处理 |
| BLOB/CLOB | 普通入口使用受大小上限保护的 Java 值和共享 codec，不把仍依赖连接生命周期的 JDBC LOB 对象交给业务层长期持有 | 不支持的驱动类型进入统一类型错误；大对象超过上限时在继续物化前失败 |
| 查询超时 | 把统一 `Duration` 向上取整为 JDBC 的整秒 `setQueryTimeout`，小于一秒也不会悄悄变成无限 | 驱动不兑现超时的情况只能由最终真实库认证识别，不能在代码层声称已强制中断 |
| JDBC 提交超时 | 自有事务在进入 `Connection.commit()` 前检查同一绝对截止点 | 标准 JDBC 没有单独限制 `commit()` 阻塞时长的 API；提交调用本身由驱动、网络和数据库超时配置治理，ORM 不创建后台线程强制中断 |
| 主动取消 | 发 SQL 前及逐行读取时检查线程中断，并尽力调用 `Statement.cancel()`；取消稳定归为 `CANCELLED` | `cancel()` 自身失败不覆盖调用方已经发出的中断事实，资源仍按 ResultSet、Statement、Connection 顺序清理 |
| 滚动结果集 | 显式高级入口请求 `TYPE_SCROLL_INSENSITIVE + CONCUR_READ_ONLY`，并在回调结束后关闭游标和语句 | 驱动不支持时直接返回稳定异常；普通 CRUD 不自动降级或改变结果集类型 |
| 保存点与专有 API | 只在已经存在的外部 JDBC 事务连接上开放，提交、整体回滚和关闭仍由上层管理 | 没有外部事务时在执行 SQL 前拒绝，不借一条新连接制造第二套事务 |

MySQL、PostgreSQL、H2、Oracle 和 SQL Server 的具体驱动版本、生成键形态、取消效果及 LOB 返回类型，统一在阶段 10
使用固定 Docker 镜像和固定驱动重新认证；认证前这里只承诺上述保守行为。

## 受影响类型门禁

V2 重点改动 `FlyingOrmClients`、同步 FormClient/Repository/Operator、Schema/Metadata 装配和两个执行器。任何已有类型达到
300 行或 20 个可调用方法时都不能继续堆职责；新增 JDBC 行为必须下沉到按连接、语句、批量、事务、结果或观测划分的
小型内部协作者。拆分不能复制同步/响应式业务规则，也不能为了行数制造只有转发作用的空壳类型。
