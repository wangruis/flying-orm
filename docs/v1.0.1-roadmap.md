# flying-orm v1.0.1 大型类治理、统一接入与执行观测增强规划

> **执行要求：** 实施时按任务逐批完成测试驱动重构，每批都必须独立验证；禁止把全部大型类一次性改完后再统一排错。

**目标：** 先在不改变既有行为的前提下治理 core/rdb 生产代码中的大型类与超大型类，再完成本文明确列出的
统一事务参与和 SQL 执行日志增强；公开 API 应尽量与 v1.0.0 保持一致。事务一致性优先于兼容，现有事务入口
确实无法安全接入外部事务时允许破坏性重构，但必须给出唯一、简单且不会误用的新入口。

**架构方式：** 收敛为少量一致的公开门面，将查询、写入、批量、渲染、映射、生命周期、连接和迁移等独立职责
下沉到包级内部组件。同步与响应式入口共享同一业务实现，不复制 SQL、安全、事务和映射逻辑。

**技术基线：** Java 21、Reactor、R2DBC、Maven 3.9、JUnit Jupiter、Checkstyle、SpotBugs、JaCoCo 和 JMH。

## 全局约束

- flying-orm 的定义不变：简单、易用、稳定、安全优先，在此基础上追求高性能、低延迟和高吞吐。
- v1.0.0 冻结基线为提交 `f22c9f4`；v1.0.1 的规划和实现只在 `1.0.1` 分支推进，不回写冻结基线。
- 大型类治理阶段的第一硬性门禁是“功能零变化”：所有既有能力、结果和运行语义必须等价。只有本文单独列出的
  统一事务参与和 SQL 执行日志增强可以新增或调整能力；事务调整必须消除双重事务控制，日志调整不能改变未开启
  日志时的执行结果和热路径行为。
- 公开 API 采用兼容优先原则：现有公开类型、方法、构造器、重载、参数、返回类型和链式调用默认保持不变；能靠
  内部职责拆分解决的问题，不得修改公开 API。
- 只有现有 API 确实阻碍职责边界、类型安全、安全约束或一致性，且不存在合理的兼容实现时，才允许删除冗余重载、
  合并重复入口、重命名、调整参数模型或重新划分类型；变更必须限制在解决问题所需的最小范围。
- 删除或改变任何公开入口前，必须建立“旧入口 -> 新入口 -> 既有能力契约”的完整迁移矩阵并记录必要性；不存在
  替代入口、能力不可达、调用结果语义改变或只是为了减少行数时，重构不得合入。
- 除执行日志增强明确扩充的观测信息外，SQL 文本与结构、参数顺序、默认配置、异常类型、错误码、事务边界、
  回调顺序、缓存失效和现有观测事件语义必须保持一致。
- 大型类治理和统一接入只修改 `flying-orm-core/src/main`、`flying-orm-rdb/src/main` 的生产实现及其直接测试、
  门禁和文档，不在本仓库增加应用框架适配模块。
- 不增加 Spring、starter、自动配置、第二套数据库执行内核或第二套同步实现。框架接入与验证放在仓库外的示例项目。
- 生产类型以不超过 300 个物理源码行和 20 个可调用方法为设计目标。
- 超过 300 行或 20 个方法必须执行职责审查；不得新增或继续扩大达到 400 行或 30 个方法的生产类型。
- 现有大型类在治理完成前只能缩小，不能继续增加实现复杂度或无必要的公开重载。
- 现有公开门面和重载优先完整保留并委托包级内部组件；只有满足上述最小必要变更门禁时才按能力去重，同步/响应式
  业务实现不得复制。
- API 破坏性简化不能成为删除边缘能力、弱化类型安全或把复杂度转移给调用方的理由。
- 不按行数机械切割，不创建无意义的一方法接口、转发层或循环依赖。
- 拆分不得增加热路径临时对象、Map 物化、Publisher 包装、反射解析、锁竞争或缓存查找。
- 事务提交、回滚、取消、`UNKNOWN`、乐观锁、逻辑删除、Tenant/Data/Field/Time Scope 和 SQL 参数绑定语义不得弱化。

## 二、目标内部边界

以下名称表示职责边界，不要求为了名称本身创建类型；只有职责确实独立并且能够单独测试时才落地。

### 2.1 表单执行边界

- `ReactiveFormClient` 只保留常用入口、依赖装配和请求编排。
- 查询、分页与 count 共享查询请求模型和 Scope 快照。
- 单行写入和批量写入共享业务条件、逻辑删除、乐观锁与字段权限处理。
- `SyncFormClient` 只在最外层执行有界等待，不重新实现查询和写入决策。
- 以能力为单位审查现有组合重载、短方法以及 `QuerySpec`、`WriteSpec`、`BatchSpec`：优先保持源码与二进制兼容，
  并统一委托同一个内部执行路径；只有兼容实现确实妨碍合理设计时才最小化收敛，且不得丢失任何既有能力或行为。

### 2.2 SQL 渲染边界

- 查询渲染负责 select、where、group、order、分页和游标结构。
- 写入渲染负责 insert、update、delete、逻辑删除和乐观锁。
- 批量渲染负责稳定列布局、参数槽和方言批量语法。
- 公共渲染上下文保存方言、标识符、参数数组和结构计划，不在不同渲染器间复制状态。
- 渲染结果继续使用参数绑定，禁止子渲染器直接拼接业务值。

### 2.3 R2DBC 执行边界

- 连接生命周期组件只负责获取、关闭、失效和清理失败观测。
- Statement 组件只负责 bind marker、参数绑定和驱动执行。
- 结果组件只负责行限制、内存限制、LOB 限制、动态行和更新行数。
- 执行保护组件只负责连接等待、SQL 超时、取消和错误翻译。
- 未配置 observer 时保留真正的无观测快速路径，避免每次执行创建无效观测对象。

### 2.4 批量与事务边界

- ATOMIC 和 INDEPENDENT 使用不同协调器，共享分片计划、参数布局和结果模型。
- 事务组件集中处理 begin、commit、rollback、取消和最终状态，不把事务状态散落在分片循环中。
- 乐观锁冲突、普通驱动失败、资源清理失败和提交结果 `UNKNOWN` 保持不同类型。
- 回执保存、完整性校验和恢复查询独立于正常写入热路径。

### 2.5 Repository 与实体边界

- Repository 负责实体语义门面，不重新实现 FormClient 的 SQL 和 Scope 逻辑。
- 生命周期回调、逻辑删除、乐观锁和批量实体跟踪分别由包级组件处理。
- 同步 Repository 委托响应式 Repository/共享实体操作组件，只在边界等待。
- `EntityMetadataResolver` 拆出的注解和访问器计划必须缓存，不能在每行映射时重新反射。

### 2.6 Schema 与客户端装配边界

- Schema 方言能力保持不可变，DDL 语法细节按表、字段、索引和外键职责组织。
- `ReactiveSchemaClient` 只编排读取、diff、审核、执行和缓存失效，不内嵌所有迁移算法。
- `FlyingOrmClients.Builder` 只收集配置；构建过程由内部装配器验证并生成不可变运行时对象图。
- 方言识别、元数据 Reader、缓存区域和执行器必须一次装配完成，运行热路径不重复推断。

### 阶段 7：统一 Java 生态接入、外部事务与 flying-orm 内部事务

当前 `R2dbcSqlExecutor` 和 `R2dbcBatchWriter` 都直接从 `ConnectionFactory` 获取连接，批量执行器还会自行执行
begin、commit 和 rollback。只传原始连接工厂时，普通操作无法加入上层事务；传事务感知代理时，普通操作
可以加入，但 `ATOMIC`/`INDEPENDENT` 又可能与外部事务争夺同一连接的事务控制权。本阶段必须从根上消除这个冲突。

- [x] 在 rdb 内建立唯一的框架无关连接/事务执行契约，统一负责连接获取、复用、释放、事务参与和所有权判断；
  `R2dbcSqlExecutor`、`R2dbcBatchWriter`、DDL、DML、FormClient、Repository 和原生 SQL 不再直接决定连接所有权。
- [x] 建立少量稳定的框架无关接入入口，统一接收类型化配置、连接能力、事务桥和 observer；纯 Java 使用者可以
  直接构建，依赖注入框架只需提供这些环境能力，不重新组装 ORM 内部对象图。租户、用户和数据权限 Scope 属于
  单次请求上下文，不进入启动期单例配置，避免把某个用户的权限错误地固化到全局客户端。
- [x] 统一基础方言选择规则：`flying-orm.dialect` 有值时显式方言优先；没有值时复用 `RdbDialectResolver` 从
  R2DBC URL 或 `ConnectionFactory` metadata 自动识别。无法识别时启动失败，不提供静默默认方言。
- [x] 框架无关 Builder 已支持代理 metadata 和动态数据源方言一致性检查。显式方言与任一物理库冲突、物理库
  之间方言不一致或物理库 metadata 无法识别时都会在启动装配阶段失败，不会创建连接或等到业务 SQL 才报错。
- [x] `FlyingOrmEnvironment` 可接收主库、从库和动态物理库清单，统一启动入口会校验全部 metadata；外部接入层
  只需把自己管理的物理库清单交给这个入口，不能复制方言判断或只检查当前恰好路由到的一个数据源。
- [x] 框架无关的 `FlyingOrmBootstrap` 已能从 `FlyingOrmConfiguration` 和 `FlyingOrmEnvironment` 一次性装配
  Executor、Reactive/Sync FormClient、Repository 工厂、DatabaseOperator、SchemaClient、MetadataReader、
  统一方言、codec、缓存、执行保护和 observer，并在启动期完成批量硬上限、日志出口和物理库方言校验。
- [x] 统一启动入口已经明确外部接入边界：接入层只绑定配置、连接工厂、事务参与器、物理数据源清单和 observer；
  业务层不手动传 renderer、dialect、executor，外部项目也不能复制客户端对象图装配代码。
- [x] 提供纯 R2DBC 默认实现：不存在外部事务时正常获取和释放连接，`ATOMIC` 批量由 flying-orm 完成
  begin/commit/rollback，提交失败继续准确报告 `UNKNOWN`。
- [x] 允许上层适配器提供外部事务绑定连接。检测到外部事务时，所有操作加入同一连接，flying-orm 不执行
  begin/commit/rollback，也不关闭外部事务拥有的物理连接。
- [x] 外部事务中的 `ATOMIC` 批量失败必须向上传递并触发外部事务回滚；成功结果只能表示 `ENLISTED`/已执行，
  在外部提交完成前不能返回 `COMMITTED`。最终状态通过外部事务终止信号和事务 observer 表达。
- [x] 外部事务中调用 `INDEPENDENT` 必须在第一条 SQL 前以稳定错误码拒绝，避免分片提交与外层原子事务互相欺骗；
  外部事务之外继续保持每个分片独立提交和逐分片结果。
- [x] 动态数据源路由键必须在事务开始前确定并在事务期间保持不变；事务读统一走主库。运行时切换到另一个物理库
  必须拒绝，单个本地事务不宣称跨数据库原子性。
- [x] 同步桥接不得在 Reactor 非阻塞线程中通过 `block()` 假装参与事务；响应式服务必须使用响应式入口。
- [x] DDL 按方言明确事务能力。会隐式提交或不支持事务 DDL 的数据库，不允许把 Schema 变更伪装成可与业务 DML
  一起回滚的事务。
- [x] 框架无关事务参与契约已接入：ORM 可借用外部事务绑定的连接，完成状态映射为 `COMMITTED`、
  `ROLLED_BACK` 或 `UNKNOWN`；事务内路由身份首次使用时锁定，切库会在 SQL 前拒绝。
- [x] 应用框架的配置绑定、依赖注入、事务连接获取、实体扫描、继承式门面和动态数据源接线不进入本仓库；这些内容
  统一在平级 `flying-orm-example` 中做接入验证，并且只能调用本阶段建立的框架无关契约。
- [x] 建立框架无关启动契约测试，覆盖不建连接完成装配、显式/自动方言校验、外部事务传播、普通 observer 与
  SQL 日志并存、缺少日志出口时启动失败，以及多个批量 observer 互相隔离。
- [x] 在 `flying-orm-example` 建立外部接入验证，覆盖连接复用、提交、回滚、取消、路由锁定、错误传播、observer
  隔离、方言识别、依赖注入和参数化原生 SQL；这些测试不进入 flying-orm 主项目的 Maven 模块。
- [x] 用契约测试覆盖无事务、外部事务提交、外部事务回滚、`ATOMIC` 参与、`INDEPENDENT` 拒绝、取消、超时、
  `UNKNOWN` 映射、连接释放和事务期间路由变化。
- [x] 以真实 PostgreSQL/MySQL 验证外部事务一致性，作为阶段 9 的最终数据库门禁。

阶段 7 的框架无关内核首批已经落地：普通 SQL 和 ATOMIC 批量会借用外部事务连接，不创建备用连接，也不执行
begin、commit、rollback 或 close；ATOMIC 执行失败会原样向上传递，INDEPENDENT 会在获取连接、订阅输入和执行
SQL 前拒绝。连接所有权现在保存在每次订阅自己的句柄中，不再通过共享 IdentityMap 和锁识别外部连接。
路由身份的非空校验与 Reactor Context 传播已有契约测试。外部 ATOMIC 成功现在明确返回 `ENLISTED`，不会再与
真正无法确认提交事实的 `UNKNOWN` 混在一起，也不会提前计算已提交影响行数。框架无关的事务终止信号已经接入：
外部提交、回滚或无法确认时会发出最终批量观测，Repository 的 POST 生命周期只在真正提交后执行。终止回调只保留
有界分片结果，不保留输入行、参数或实体。事务期间的显式数据库路由现在会与锁定身份比较，不一致时在获取连接、
订阅批量输入和执行 SQL 前拒绝；合法查询继续复用上层提供的主库事务连接，不再经过可能选择从库的路由工厂。
同步桥现在会在 Reactor 非阻塞线程上于订阅数据库操作前拒绝等待，普通线程和虚拟线程仍可作为明确的同步边界。
DDL 已按方言区分可参与事务和隐式提交，并会在不安全的外部事务组合中于第一条 SQL 前拒绝。类型化配置、运行环境
和统一启动入口现已落地，配置对象不读取 YAML，运行环境也不依赖具体容器。平级 `flying-orm-example` 已使用
Spring Boot 3.5.16 和 H2 R2DBC 完成第三轮外部接入验证：`flying-orm` 根配置、显式/自动方言、统一 Bootstrap、
依赖注入、继承式 CRUD、Spring 事务提交/回滚、外部 ATOMIC 的 `ENLISTED` 与最终 `COMMITTED/ROLLED_BACK`、外部
INDEPENDENT 预执行拒绝、事务路由锁定、命名参数原生 SQL、安全 SQL 日志、observer 故障隔离，以及连接获取
超时和普通 SQL 执行中途取消，示例全部 10 个测试通过。本轮发现并修复统一 Builder 的装配顺序问题：observer
现在先进入真正持有事务完成回调的 R2DBC 执行器，再套批量内存上限，最终事务状态不会丢在内层空 observer。
ORM 自有连接取消释放、Spring 事务内单连接复用和一次释放、外部事务 `UNKNOWN` 容器映射均已建立契约测试；
真实 PostgreSQL/MySQL 最终门禁已经完成：两库都验证了外部事务提交、回滚、ATOMIC 最终状态、
INDEPENDENT 预执行拒绝和最终数据行数，结果见阶段 9 认证报告。

### 阶段 8：补齐可配置的 SQL 执行日志

这项任务建立在现有 `SqlExecutionObserver` 和 `BatchExecutionObserver` 上，不再复制一套执行链。core/rdb 只提供
框架无关的观测数据、展示策略和安全边界，不读取 YAML，也不依赖 Spring 或具体日志框架；外部适配器负责把
规范前缀固定为 `flying-orm`，并将其中的 `sql-log` 配置绑定为 observer，不得同时维护其他配置前缀别名。

- [x] 保留现有参数化 SQL，同时按显式配置生成仅供排查使用的完整展示 SQL；展示 SQL 不得回流为数据库执行文本。
- [x] 支持记录 SQL 类型、执行状态、耗时、参数数量、查询返回行数以及 insert/update/delete 的影响行数。
- [x] 支持记录 `EXTERNAL`、`INTERNAL`、`AUTO_COMMIT` 事务来源；上层可进一步标记自己的事务实现，
  但 core/rdb 不引用任何应用框架类型。
- [x] 参数值和完整展示 SQL 默认关闭；启用后执行统一的敏感值脱敏、单值截断、SQL 总长度限制和异常文本清理。
- [x] 对原生 SQL 中无法可靠识别语义的参数明确安全边界，不把“猜测字段名”当作可靠脱敏；允许上层提供额外的
  脱敏规则，但不得允许规则关闭框架的硬性长度与类型保护。
- [x] 批量分片和汇总事件默认输出输入数、影响行数、分片位置、当前/最终状态和失败分类；日志不订阅、不复制批量
  参数 Publisher。单条汇总日志已经带上分片总数、成功数和失败数；流式入口只在当前订阅的固定大小累加器中计数，
  不保存分片列表，也不在日志 observer 中维护共享并发状态。
- [x] 未启用日志或对应日志级别不可用时，不拼接完整 SQL、不复制参数集合、不创建逐行日志事件，保留快速路径。
- [x] observer 或上层日志组件失败时不得改变 SQL 的成功、失败、取消和事务结果。
- [x] 在 `flying-orm-example` 验证上层 YAML 承接 `enabled`、`level`、`full-sql`、`parameters`、
  `affected-rows`、`returned-rows`、`duration`、`slow-threshold`、`max-length` 以及批量摘要配置；
  这些配置不进入 core/rdb。
- [x] 用少量契约测试覆盖默认关闭 SQL/参数、显式 SQL 文本、敏感值脱敏、长度限制、返回/影响行数、批量摘要、
  自动事务来源和 observer 失败隔离，并验证执行器只在日志明确需要时传递参数值。
- [x] 补齐由实际执行上下文自动判断事务来源的契约测试，并确认事务参与器在同一执行中只查询一次。
- [x] 比较关闭日志前后的分配与延迟。短 JMH 使用立即完成的 Publisher 排除数据库 I/O：默认关闭日志的装配快路径

## 五、完成标准

v1.0.1 只有同时满足以下条件才算完成：

- 15 个大型/超大型类型全部完成治理，不把代码转移到新的大型类。
- core/rdb 不存在本版本新增的 400 行或 30 方法生产类型。
- v1.0.0 的全部现有功能和调用结果完整保留；除本文明确列出的统一接入、事务参与和 SQL 执行日志增强外不增加
  其他功能，确需变化的旧 API 能力都有已验证的新入口。
- 公开 API 与 v1.0.0 尽量保持一致，所有不兼容变化都是有证据的最小必要变更并具有完整迁移说明；公开门面职责
  清晰，内部没有同步/响应式重复实现。
- SQL、参数顺序、安全 Scope、逻辑删除、乐观锁和实体生命周期契约有自动化测试保护。
- 事务、取消、连接释放、批量冲突和 `UNKNOWN` 结果语义保持正确。
- 外部事务与内部事务不会同时控制同一连接；普通操作和 `ATOMIC` 能正确加入外部事务，外部事务中的
  `INDEPENDENT` 在执行前稳定拒绝，事务期间不能切换物理数据库。
- 纯 Java 启动入口能够根据类型化配置和连接环境完成统一装配；方言缺省时自动识别，业务不必手动创建或传递
  renderer、dialect、executor 等 ORM 内部基础设施对象。
- 外部示例证明应用容器能够通过同一接入契约完成装配；接入方式差异不能改变查询、写入、安全和事务语义。
- SQL 执行日志能够由上层配置开启；关闭时不生成完整 SQL 和参数副本，开启时具备脱敏、截断、批量摘要、
  返回/影响行数及事务来源信息，日志失败不影响数据库操作。
- 全量质量门禁、发布制品门禁和受影响真实数据库认证通过。
- 性能结果至少不低于重构前稳定多轮基线；所有性能结论包含参数、样本和原始证据。

## 六、明确不做

- 除本文明确批准的统一接入、事务参与和 SQL 执行日志增强外，不新增、修改或删除其他功能。
- 不改变 SQL 结构、参数顺序、默认值、事务边界、安全 Scope、缓存、观测、生命周期和同步等待语义。
- 不在本仓库增加 Spring、starter、自动配置或其他应用框架模块。应用框架接入代码与验证只放在仓库外的示例项目，
  示例不得复制 ORM 内核。
- 不把纯内部组件作为公共 API 暴露；新公开入口只用于更简单地承载既有能力。
- 不用降低安全校验、事务持久性或资源上限换取更短代码或更好跑分。
- 不以“简化 API”为名删除能力、改变结果、弱化异常契约或迫使调用方绕过类型安全和安全边界。
- 不为了类行数、方法数或形式上的整洁主动制造不必要的 API 不兼容。
- 不把 testkit、benchmark 或认证脚本当作生产模块。
